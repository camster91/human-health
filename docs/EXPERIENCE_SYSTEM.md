# Experience System — Simple, Visual, Delightful

## Experience promise

Human Health should feel like a capable guide that already understands the person, not a terminal that waits for prompts.

Most sessions should require almost no typing.

## First open

The shortest useful onboarding:

1. one primary goal;
2. normal available time;
3. equipment;
4. optional health/safety context;
5. start the first useful action.

Everything else can be learned progressively.

## Today

Default layout:

- one clear recommendation;
- duration;
- intensity;
- one-sentence reason;
- one large Start button;
- small context actions:
  - I have less time
  - I'm sore
  - Something hurts
  - Change equipment
  - Ask Guide

Do not require the user to select from a program library every day.

## Workout/session mode

Show one task at a time.

Typical exercise card:

- movement name;
- short loop or image;
- target sets/reps/time;
- previous relevant performance;
- large action controls.

Feedback:

- Too easy
- Good
- Hard
- Pain

The next step updates automatically.

Rest should be handled in the same flow with timer, pause, skip, and voice support.

## Minimum useful day

If normal training does not fit, the app should offer a safe minimum useful alternative instead of marking the day failed.

Examples:

- 6–10 minute strength minimum;
- short walk;
- mobility reset;
- recovery day;
- breathing/downshift;
- rest.

The user should always know that reduced work can still count as the correct plan.

## Body

Use an interactive front/back body model.

Areas can show:

- recently trained;
- ready;
- recovering;
- tight;
- sore;
- user-reported pain;
- mobility focus;
- capability trend.

Tap an area and choose simple state controls rather than typing.

The app can then adapt today's plan or open a focused Guide flow.

## Progress

Avoid one universal health score.

Prefer meaningful trajectories:

- strength;
- aerobic/cardio;
- mobility;
- balance/coordination;
- consistency;
- recovery;
- user-selected quality-of-life goals.

Progress views should answer:

- What is improving?
- What is stable?
- What needs attention?
- What should I do next?

## Guide

The Guide can accept text or voice, but responses should render into the most useful UI.

Examples:

"I only have 10 minutes" → revised plan card.

"Show me this exercise" → short trusted video.

"Why are we doing this?" → concise explanation.

"I'm travelling" → equipment/location-aware plan.

"I want to go outside" → walk/outdoor option and route when available.

"What's changed over the last three months?" → chart + short summary.

The response does not need to look like a chat bubble if another component communicates better.

## You

Contains:

- goals;
- personal rules;
- equipment;
- coaching style;
- health modules;
- integrations;
- privacy/data;
- what the app believes it knows;
- corrections;
- exports/deletion.

## Coaching style

User-selectable styles can include:

- Calm
- Direct
- Educational
- Encouraging

Style changes wording, not safety logic or underlying decisions.

## Delight principles

Use:

- strong visual hierarchy;
- immediate response to taps;
- smooth state transitions;
- short meaningful motion;
- useful haptics where available;
- beautiful media;
- full-screen focus during sessions;
- completion moments that feel satisfying;
- clear empty/offline states.

Avoid:

- childish mascots unless intentionally designed later;
- fake praise;
- confetti for trivial behaviour;
- red failure states for missed workouts;
- streak flames;
- dense settings on primary screens;
- excessive AI typing animations;
- chat-first layout everywhere.

## Media

Preferred exercise teaching stack:

1. 2–5 second silent loop;
2. tap for full demonstration;
3. optional cues;
4. optional common mistakes;
5. deeper learning only on request.

Do not make every session depend on watching a long video.

## Voice

Voice should make active sessions more screen-free:

- announce next exercise;
- start rest;
- accept "done", "skip", "hard", or "pain";
- read short cues;
- keep responses brief during physical activity.

Voice is an interaction mode, not a separate assistant persona.

## Camera — later

Optional camera support can provide low-risk movement feedback such as rep count or tempo.

Any camera feature requires:

- explicit opt-in;
- clear on-device/remote-processing disclosure;
- no hidden recording;
- deletion controls;
- conservative claims;
- graceful manual fallback.

## Contextual web experiences

External context can become product UI:

- weather → indoor/outdoor choice;
- map → walk/run route;
- hotel/gym context → equipment-aware session;
- research → evidence card;
- image/video → visual instruction.

The user should experience the result, not the search process.

## Long-term relationship

### First month

Learn preferences, equipment, normal duration, baseline capability, and what the user actually completes.

### First year

Improve consistency, movement literacy, strength, cardio, mobility, and recovery while keeping the app simple.

### Later years

Adapt priorities as goals, schedule, injuries, life stages, aging, and health context change.

The interface should not get progressively more cluttered merely because the backend knows more.

## Quality-of-life checkpoints

Occasionally ask questions that matter outside the app:

- Are stairs easier?
- Do you feel stronger?
- Are sessions fitting your life?
- Is a recurring sore area improving?
- Can you do activities you care about more comfortably?

These outcomes should influence planning.

## Accessibility

Treat accessibility as part of delight:

- large tap targets;
- screen reader semantics;
- Dynamic Type/text scaling;
- reduced motion;
- high contrast;
- captions/transcripts;
- voice alternatives;
- landscape/tablet support where useful;
- controls usable with reduced dexterity.

## No-terminal rule

If a user needs to repeatedly type prompts to get normal value, the design has failed.

The Guide should proactively compose the experience from known context, while preserving easy user override.
